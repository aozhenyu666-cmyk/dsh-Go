# ADR 001 · 拦截状态的持久化：单一原子快照

状态：**已采纳** · 日期 2026-11-01 · 阶段 4B

## 背景

一次拦截由两份文件描述：`guard.json`（config、open 事件、冷却、白名单）与 `ledger.json`
（回执与五个计数）。每次状态推进至少写两份。两份各自原子（临时文件 + flush + fsync +
原子替换 + 目录 fsync，见 `AtomicJsonFile`），**但合起来不原子**：崩在两次 rename 之间，
磁盘上就留下一个自相矛盾的状态。阶段 4 已经能**检测**这种不一致（`splitWrite`），但没有消除它。

## 三个候选

| | 方案 | 改动量 | 崩溃一致性 | 结论 |
|---|---|---|---|---|
| A | 单一原子 JSON 快照 | **小**：复用 `AtomicJsonFile`，把两处写合成一处 | 完整：一次 rename = 一次提交 | **采用** |
| B | SQLite 单事务 | 大：引入 C 依赖 + 迁移 + 打包体积 | 完整 | 拒绝：为 4 个计数引入数据库不成比例 |
| C | Event log + snapshot | 中：新增日志格式 + 重放 + 压缩 | 完整 | 拒绝：回执上限 100、状态很小，收益抵不上复杂度 |

## 决策

建立 `InterceptRepository`，单文件 `intercept.snapshot.json`，一次操作一次提交。

```json
{
  "schemaVersion": 1,
  "config": { ... },
  "guardState": { ... },
  "ledgerState": { ... },
  "appliedEventIds": [ ... ],
  "lastCommittedTransactionId": 42
}
```

**关键约束**：不是「两个类共用一个 `AtomicJsonFile` 然后各写各的」——
那只是把两个文件换成一个文件、仍然两次写。必须是**统一的事务所有者**在一次调用里提交完整状态。

实现上：`InterceptGuard` 的 mutating 公开方法就是事务边界（`onForeground` / `onPageShown` /
`onReleased` / `onExited` / `onPaused` / `onUnavailable` / `expireOpen` / `setConfig` / `recover`）。
Guard 的 `persist()` 改为 `repo.commit(...)`；Ledger 被某仓库持有时其 `persist()` 只改内存，
由 Guard 那一次提交带上它。Ledger 独立使用时（现有单测）保持原有自持久化行为。

## 写入协议（每次提交）

1. 取完整旧快照（内存已有，不必读盘）
2. 计算完整新快照
3. 校验内部一致性（计数 >= 回执数、白名单子集于放行来源、eventId 不重复）
4. 写临时文件 5. flush 6. fsync 7. 原子替换 8. 目录 fsync
9. **重新读取并比对**，确认落盘的就是刚算出来的那份
10. 只有第 9 步通过才更新内存状态并返回成功

写失败时：内存不前进、不返回成功、不产生 RELEASED 回执、旧快照仍可读。

## 迁移

`guard.json` + `ledger.json` 同时读入 → 一致性校验 → 生成快照 → 写入 → 回读验证 → 标记完成。
旧文件保留为 legacy 备份。任何不一致都**标 RECOVERY_REQUIRED 并停**，不猜、不删、不伪造白名单。

## 后果

- 好：崩溃后不可能出现「计数有、回执无」或「白名单丢」的矛盾状态。
- 好：一次操作一次 fsync，比原来两次更省。
- 坏：快照比单份文件大约两倍，但状态本身很小（回执上限 100 条）。
- 风险：迁移一次性不可逆（旧文件只读保留），首次启动多一次写。

# ADR 002 · 授权语义（D5）

状态：**已采纳** · 日期 2026-11-01

| 结局 | 计有效拦截 | 产生访问冷却 | 放行 | 重开目标 APP |
|---|---|---|---|---|
| NOT_SHOWN | 否 | 否 | 否 | **立即再拦** |
| BLOCKED | **是** | **否** | 否 | **立即再拦** |
| EXITED | **是** | **否** | 否 | **立即再拦** |
| RELEASED | 是 | — | 是（`releaseUntil`） | 到点后重新拦 |
| PAUSED | 是 | — | 是（`pauseUntil`） | 到点后重新拦 |
| WHITELIST | 是 | — | 永久 | 不拦，直到撤销 |

**核心更正**：`cooldownMs` 与 `dailyMax` 都**不得**作为放行理由。
冷却只用来控制「多久之后再弹一次题」，绝不能变成「这段时间随便用」。
`dailyMax` 是用户主动设的**软上限**（减少打扰），不是严格模式的替代品；`0` 表示不设这个上限。

要达到「降低弹题频率」的目的，用独立的技术退避（`InterceptDeadline.Backoff`），
**不得**借它向目标 APP 发放访问许可。

# ADR 003 · 展示失败时不得隐形放行（D2）

状态：**已采纳** · 日期 2026-11-01

页面启动失败时，目标 APP 仍在**前台可交互**。旧代码在 `backoff.isHoldingOff()` 处直接 `return`，
等于「技术上放弃了，但行为上放行了」。这不是授权，是漏洞。

正确链条：启动失败 → 记 NOT_SHOWN（退还额度与冷却）→ **尝试用已授权的无障碍服务回 HOME** →
重新读取前台 → 确认目标 APP 已离开。HOME 失败则记 `ENFORCEMENT_UNAVAILABLE` 并告知用户，
**不记 BLOCKED、不伪造成功回执**。15 秒退避只控制「多久之后再试着弹」，与放行无关。

系统的物理限制要如实说明：普通应用无法保证绝对阻断（用户可以用 Home 手势、最近任务、
系统设置绕过），我们能保证的是**不放行、不误记、如实报告**。
